A design system when half the contributors are machines

I wrote the same rule twice, in two toolchains, eight months apart. The first time it was a document. The second time it could stop me.

Where
PlaySesh (2025–2026) and y30 (2026)
Role
Author of the tokens, the primitives, and the rules that govern them
Contributors
Three humans and a coding agent, across 1,793 commits
Stack
React, TypeScript, Radix, CSS custom properties, Cursor rules, Claude Code hooks

A design system's real test is what happens when someone ignores it. Increasingly that someone is a language model with no memory of why the rule exists.

At PlaySesh I wrote the rule as a document the agent reads. 171 hardcoded colors got past it. At y30 I made it block the commit.

The problem, stated plainly

A design system has always depended on people choosing to follow it. Code review, taste, a shared sense that the thing should look like itself. That worked because contributors accumulate context: you learn where the tokens live, you get told off once, you stop reaching for hex.

An agent accumulates nothing. Every session it arrives fresh, competent, fast, and completely unaware that #3b82f6 already has a name. It will write plausible, working, off-system code all day, and it will do it faster than you can review.

So the question stops being is the system well designed and becomes is the system legible and enforceable to a reader with no memory. Those are different problems, and only one of them is solved by a Figma library.

What the demo is actually doing

The substitution is not a lookup table written for this page. It resolves your input against the real token scales, exact match first and then nearest value, the same way the hook does. Type padding: 20px and it will tell you the system has no 20, and offer you the 24 it does have. That is the interesting case, because it is where a system either bends or grows a one-off.

My rule for that case, verbatim from the y30 conventions:

If the token doesn't exist, do not add a one-off value. File an entry in docs/design/inconsistencies.md describing the gap, and either ask the user for direction, or pick the nearest existing token and live with the small visual delta.

The design system is a contract. Every drift compounds.

The system the rules protect

PlaySesh's tokens are the first thing in the repo. Commit a812e20, day one, before the canvas, before auth, before anything worth looking at. Semantic rather than raw, so a component asks for a role and not a colour.

Spacing, and the two systems that had to agree

PlaySesh runs a seven-step named scale; y30 runs a ten-step 4px grid. Different products, different needs, same discipline: a component never states a number.

The layering contract

The token nobody thinks of as a design token, and the one that saves the most time. Six values, ordered once, so nobody ever argues about whether a tooltip goes above a modal.

    Where it held: two libraries down to one

    The real test came from inside the team. A co-founder introduced react-tooltip for one panel while the rest of the app used the Radix tooltip I had built on top of the tokens. Two tooltip implementations, two visual languages, two things to maintain.

    I wrote the assessment, made the call, and did the migration:

    Issue: UndoRedoPanel uses react-tooltip while the rest of the app uses Radix Tooltip.
    Impact: Inconsistent styling · different behavior · maintenance overhead of two libraries · hardcoded values, which violates the design tokens.

    ✓ Removed react-tooltip · ✓ migrated the panel to the custom Tooltip · ✓ all tooltips now on one implementation.

    The dependency came out of package.json in commit 4b02ae7. That is the part I would point at: not that I wrote a standard, but that the standard survived someone else's reasonable decision and the losing library was actually deleted rather than left to rot alongside the winner.

    The same cycle ran on dropdowns, and ended in client/utils/dropdownAnimations.ts: three shared constants and three keyframes, now imported by eight components that each used to carry their own copy.

    Where it failed, and what I did about it

    At PlaySesh the rule was a document. Good writing, injected into every agent edit, unambiguous. And it did not hold: 171 hardcoded colour declarations are still in that codebase, written past a rule that says in bold capitals never to write them.

    An advisory rule is a suggestion with extra steps. That is the lesson, and it cost a real number.

    So at y30 I built the version that can say no. It came out of a specific failure: an agent, working in a repo where the token file had never been wired into the Vite build, could not find any tokens, so it invented a parallel set, web/src/care/tokens.ts, with its own hex values. Entirely reasonable behavior. Catastrophic for a design system.

    The fix is layered by cost, because the cheapest correction is the one that happens before anything is written:

    Read time. "Before writing or editing any file under web/src/, you MUST have read… If you cannot cite at least one existing CSS variable that applies to your work, you are not ready to write. Ask the user, or read more."

    Write time. A PostToolUse hook scans the edit and names the exact substitution, so the agent self-corrects mid-task. Deliberately non-blocking: a warning it can act on beats a wall it has to argue with.

    Commit time. A PreToolUse hook intercepts git commit and exits 2. This one is a wall.

    Advisory, corrective, blocking. Most codebases have none of these. The useful insight is not that blocking works, which it obviously does. It is that blocking alone is a bad experience, and the warning layer is what makes the wall rare enough to tolerate.

    What is not true here

    Every claim above has a commit behind it. These do not, and a system page that only lists wins is a system page nobody should trust.

    • Neither system is fully adopted. PlaySesh: 87 of 149 component files import the tokens, and those 171 hardcoded colors are still there. y30 is roughly half-migrated, 935 token references against 923 raw hex.
    • There is no single source of truth. Both repos carry two token layers, a TypeScript object and a CSS custom-property layer, that are not generated from each other, and in PlaySesh their primary blues do not even match. A build step should own this. None does.
    • Accessibility is written down, not enforced. WCAG AA is in the rules and the primitives implement focus-visible and real touch targets, but there is no axe, no jest-axe, no lint rule, and nothing in CI that could fail on a contrast regression. This is the first thing I would fix.
    • No versioning, no changelog, no visual regression. The system was never packaged or distributed, so there was nothing to version against.
    • The blocking hook covers agent commits. It fires when the commit runs through the agent's shell. A human committing in a terminal walks straight past it. A real git hook is the obvious next move.
    • There is still a duplicate Button in PlaySesh. A second implementation with hardcoded hex, added by a co-founder during a login push, shipping alongside mine. I never resolved it. It is the honest counterexample to the tooltip story directly above.

    Scale, stated accurately: one repo of about 1,800 commits with three humans and an agent, and one repo of about 1,400 that is me and agents. This is not a system that governs forty engineers. It is a system that held a small team and a machine to one visual language for six months, and I can show you every place it leaked.
